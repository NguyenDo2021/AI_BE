# Customers and sales orders API

Base URL: `/api`. All endpoints require `Authorization: Bearer <accessToken>`.
Responses are direct JSON objects; no `data` wrapper. UUIDs are strings, dates are
`YYYY-MM-DD`, audit timestamps are ISO-8601 UTC. Optional/null response fields are
omitted by the existing Jackson configuration. POST create returns 201; other
successful operations return 200. No DELETE endpoint is provided.

## Authorization

| Endpoint | Employee permission |
|---|---|
| GET /customers, GET /customers/{id} | CUSTOMER_VIEW |
| POST /customers | CUSTOMER_CREATE |
| PUT /customers/{id} | CUSTOMER_UPDATE |
| GET /sales-orders, GET /sales-orders/{id} | SALES_ORDER_VIEW |
| POST /sales-orders | SALES_ORDER_CREATE |
| PUT /sales-orders/{id} | SALES_ORDER_UPDATE |
| POST /sales-orders/{id}/confirm | SALES_ORDER_CONFIRM |
| POST /sales-orders/{id}/cancel | SALES_ORDER_CANCEL |

The live active ADMIN role bypasses functional permission and warehouse assignments.
Employees must have the endpoint permission AND a current database assignment to
the warehouse. Each request checks assignments; an old JWT cannot retain a revoked
warehouse. SALES_ORDER_CONFIRM alone permits confirmation within assigned warehouses;
receipt permissions are not needed. Actors come from the authenticated session.
Functional authorities follow the existing JWT mechanism.

Lists restrict visible warehouses before count/pagination. Explicitly requesting a
warehouse outside the user's scope returns 403. Detail and all mutations also check
scope, including successful idempotent confirm/cancel retries.

## Customers

### GET /customers

Optional query fields: `warehouseId` UUID; `keyword` text (case-insensitive literal
substring in code/name/phone); `status` integer 0 or 1; `page` default 1, minimum 1;
`pageSize` default 10, range 1..100. Sort: createdAt descending, then id descending.

Response: `{ "items": [CustomerResponse], "total": 1, "page": 1, "pageSize": 10 }`.
`total` counts all matching visible records, even if the requested page is empty.

### GET /customers/{id}

Returns CustomerResponse or 404 CUSTOMER_NOT_FOUND. Inactive customers remain visible.

### POST /customers

| Field | Required | Validation |
|---|---|---|
| warehouseId | yes | existing active warehouse within scope |
| name | yes | nonblank, <=160 characters; trimmed |
| phone | no | <=20 characters; duplicates allowed |
| address | no | <=500 characters |
| note | no | <=2000 characters |
| status | yes | JSON integer 0 or 1, no numeric strings/floats |

`id`, `code`, `createdAt`, `updatedAt` are generated by the backend. Code is `KH-`
followed by 32 UUID hex characters, with a database unique constraint.

### PUT /customers/{id}

Full replacement of name, phone, address, note, status. Same validation as POST;
`warehouseId` may be omitted, but if sent must equal the existing warehouse.
Omitted optional contact fields become null. The warehouse, id, code and createdAt
remain fixed. Updates (including deactivation) are allowed in an inactive warehouse
within scope. Deactivate using `status: 0`. Foreign keys prevent deleting referenced
customers; the API does not expose deletion.

### Customer example

POST `/api/customers`:
```json
{"warehouseId":"11111111-1111-1111-1111-111111111111","name":"Customer A","phone":"0900000000","address":"Address A","note":"Delivery contact","status":1}
```

PUT `/api/customers/22222222-2222-2222-2222-222222222222`:
```json
{"name":"Customer A updated","phone":"0900000000","address":"Address B","status":0}
```
200 response:
```json

  "id": "22222222-2222-2222-2222-222222222222",
  "warehouseId": "11111111-1111-1111-1111-111111111111",
  "code": "KH-22222222222222222222222222222222",
```

## Sales orders

### GET /sales-orders

Optional filters: `warehouseId` UUID, `customerId` UUID, `status` DRAFT/CONFIRMED/CANCELLED,
`from`, `to` dates, `page` default 1, `pageSize` default 10 (1..100).
Date filtering is by **saleDate**, inclusive at both ends. from > to returns 400.
A customer filter does not broaden warehouse scope. Sort: createdAt descending,
then id descending. Response `{items: [SalesResponse], total, page, pageSize}`.

### GET /sales-orders/{id}

Returns the full SalesResponse including lines, computed totals, version, audit and
customer snapshot when confirmed (retained after cancellation).

### POST /sales-orders

| Field | Required | Validation |
|---|---|---|
| warehouseId | yes | existing active warehouse within scope |
| customerId | no | null/omitted means walk-in; otherwise existing, active, same warehouse |
| saleDate | yes | date YYYY-MM-DD |
| note | no | <=2000 characters |
| discountAmount | no | JSON integer >=0, default 0 for omitted/null, <=subtotal |
| lines | yes | array of 1..1000 nonnull lines, distinct productId |
| lines[].productId | yes | existing active product |
| lines[].quantity | yes | JSON integer 1..9223372036854775807 |
| lines[].unitPrice | yes | JSON integer 0..9223372036854775807 (VND) |

Strict numeric deserialization rejects decimals (including 1.0), exponents represented
as floating tokens, numeric strings and values beyond signed Long. Backend uses
Math.multiplyExact/addExact/subtractExact. lineTotal = quantity * unitPrice;
subtotal = sum(lineTotal); totalAmount = subtotal - discountAmount.
All computed amounts and balances must fit Long.MAX_VALUE. Prices may be zero.

Only request DTO fields are consumed. Client lineTotal/subtotal/totalAmount/status/code/
snapshot/audit/actor fields are ignored and cannot override server calculations or
identity. The actual unitPrice never updates the product catalog's defaultSalePrice.
Generated order code: `BH-` plus 32 UUID hex characters; database enforces uniqueness.
Create produces DRAFT with version 0, with no inventory movement.

### PUT /sales-orders/{id}

Full replacement: saleDate, customerId, note, discountAmount, lines, plus required
`version` (JSON integer >=0). Optional warehouseId must match the existing warehouse.
Omitted customerId/note clear those fields; omitted/null discountAmount resets to zero.
Only DRAFT may be edited. Warehouse/customer/product activity is checked again.
Successful edit increments version once and updates updatedAt; inventory is unchanged.

### POST /sales-orders/{id}/confirm

Body `{ "version": 0 }`, required nonnegative strict JSON integer.
Only DRAFT transitions to CONFIRMED. Backend rechecks active warehouse/products/customer,
locks the same warehouse row used by receipt operations, locks the document and
products, validates **all** stock, then subtracts every quantity and records negative
SALE_CONFIRM movements in one transaction. A failure rolls back lines/snapshots,
balances, movements, status/version/audit.

At confirmation, product code/name/unit are refreshed and frozen in lines. A separate
customerSnapshot freezes code/name/phone/address; walk-in orders freeze the label
`Kh\u00e1ch l\u1ebb` (Vietnamese walk-in label) without an id/code. No later catalog/customer edits
change a confirmed response. Reconfirming CONFIRMED returns its current response even
with a stale version, inactive catalog or warehouse, with no new inventory/version.
Confirming CANCELLED returns 409 INVALID_SALES_ORDER_STATUS.

### POST /sales-orders/{id}/cancel

Body `{ "version": 1, "reason": "All goods recovered", "goodsReturned": true }`.
version is required strict nonnegative integer; reason is required, nonblank, <=2000
characters. goodsReturned is optional for DRAFT, but must be true for CONFIRMED.
The confirmation means all goods were recovered or had never been delivered.
DRAFT cancellation creates no movement. CONFIRMED cancellation adds exactly all
original quantities, writes positive SALE_CANCEL movements, and preserves snapshots.
It is allowed even when warehouse/customer/product catalog records are inactive.
Cancellation increments version once. CANCELLED is final; repeat cancel returns the
current order without changing stock/version/audit (request validation and permission/
scope checks still apply). Partial returns are not supported.

### SalesResponse schema

| Field | Type / presence |
|---|---|
| id, code, warehouseId | UUID, string, UUID; always |
| customerId | UUID; omitted for walk-in |
| saleDate, note | date; optional string |
| status | DRAFT / CONFIRMED / CANCELLED |
| subtotal, discountAmount, totalAmount, version | signed 64-bit nonnegative integers; always |
| createdBy, createdAt, updatedAt | UUID, UTC timestamp, UTC timestamp; always |
| confirmedBy, confirmedAt | UUID/timestamp after successful confirmation, retained on cancel |
| cancelledBy, cancelledAt, cancellationReason | UUID/timestamp/string when cancelled |
| goodsReturned | boolean when supplied on draft cancel, always true on confirmed cancel |
| customerSnapshot | {code?, name, phone?, address?} only after confirmation, retained on cancel |
| lines | [{productId, quantity, unitPrice, lineTotal, productCode, productName, unit}] |

Draft line product fields are the catalog values at the last create/edit. Confirmation
refreshes them. Lines are returned sorted by product UUID. Snapshots are invoice data;
this module does not infer payment, receivables or electronic invoice status.

## Inventory movement schema (backward compatible)

GET `/api/warehouses/{warehouseId}/inventory-movements` retains the existing filters
`productId`, `from` inclusive UTC instant, `to` exclusive UTC instant, page/pageSize,
and INVENTORY_MOVEMENT_VIEW permission. No type filter is introduced.
Response `{items:[MovementResponse],total,page,pageSize}`.

| Field | Type |
|---|---|
| id, warehouseId, productId | UUID |
| quantityChange | signed long, nonzero |
| type | RECEIPT_CONFIRM (+), RECEIPT_CANCEL (-), SALE_CONFIRM (-), SALE_CANCEL (+) |
| receiptId, receiptCode | receipt source only; omitted for sales |
| salesOrderId, salesOrderCode | sales source only; omitted for receipts |
| productCode, productName, unit | frozen source-line strings |
| performedBy, performedAt | authenticated UUID, UTC instant |

```json
{"id":"66666666-6666-6666-6666-666666666666","warehouseId":"11111111-1111-1111-1111-111111111111","productId":"33333333-3333-3333-3333-333333333333","quantityChange":-10,"type":"SALE_CONFIRM","salesOrderId":"44444444-4444-4444-4444-444444444444","salesOrderCode":"BH-44444444444444444444444444444444","productCode":"P001","productName":"Product 1","unit":"cay","performedBy":"55555555-5555-5555-5555-555555555555","performedAt":"2026-10-09T02:02:00Z"}
```
A sales id is never placed in receiptId. Source/sign CHECK and compound line FK
validate source identity. UNIQUE(source id, product id, type) prevents duplicate
movements. Receipt confirm/cancel signs and existing fields remain unchanged.

## Errors

Existing error envelope: `{timestamp, status, code, message, details}`. `details` is
an object of field/path to validation message; usually empty for business errors.

| HTTP | Code | Trigger |
|---|---|---|
| 400 | INVALID_REQUEST | malformed JSON/UUID/date/enum, fractional/string/out-of-range numeric token, invalid status filter |
| 400 | VALIDATION_ERROR | missing required values, length/range/nonblank/line count violations |
| 400 | INVALID_PAGINATION | invalid service pagination (controller may return VALIDATION_ERROR) |
| 400 | INVALID_DATE_RANGE | from > to |
| 400 | DUPLICATE_PRODUCT | repeated productId |
| 400 | INVALID_DISCOUNT | discountAmount > subtotal |
| 400 | GOODS_RETURNED_REQUIRED | confirmed cancel without goodsReturned=true |
| 401 | UNAUTHORIZED | missing/invalid/expired session or inactive current account, per existing security |
| 403 | FORBIDDEN | missing endpoint permission |
| 403 | WAREHOUSE_ACCESS_DENIED | warehouse outside current database assignment |
| 404 | WAREHOUSE_NOT_FOUND | warehouse does not exist (admin/in-scope lookup) |
| 404 | CUSTOMER_NOT_FOUND | unknown customer |
| 404 | PRODUCT_NOT_FOUND | unknown product |
| 404 | SALES_ORDER_NOT_FOUND | unknown sales order |
| 409 | WAREHOUSE_IMMUTABLE | PUT tries to change warehouse |
| 409 | WAREHOUSE_INACTIVE | create/edit/confirm in inactive warehouse |
| 409 | CUSTOMER_INACTIVE | selected customer inactive at create/edit/confirm |
| 409 | CUSTOMER_WAREHOUSE_MISMATCH | customer belongs to another warehouse |
| 409 | PRODUCT_INACTIVE | inactive product at create/edit/confirm |
| 409 | INVALID_SALES_ORDER_STATUS | update final order, confirm cancelled order |
| 409 | VERSION_CONFLICT | stale version for actual edit/state transition |
| 409 | INSUFFICIENT_STOCK | not enough stock for every sale line or receipt reversal |
| 409 | NUMERIC_OVERFLOW | computed line/subtotal/balance/version would exceed Long.MAX_VALUE |
| 409 | RESOURCE_CONFLICT | database integrity constraint failure; transaction rolled back |
| 405 | METHOD_NOT_ALLOWED | unsupported DELETE |
| 500 | INTERNAL_ERROR | unexpected server failure, existing handler |

Reload after VERSION_CONFLICT. Confirm/cancel retries only bypass version checking
when already in the target state; requests must still contain valid required fields.
No payments, debt, electronic invoicing, warehouse transfer, partial delivery/returns
are implemented. A future payment module can reference the immutable order UUID.

## Payment integration
Sales responses now include paidAmount, remainingAmount and paymentStatus. DRAFT/CANCELLED have remainingAmount=0 and omit paymentStatus. CONFIRMED zero-total orders are PAID. Cancelling an order with active payments returns 409 SALES_ORDER_HAS_PAYMENTS; no refund is implemented. See [payment contract and schemas](payments-api.md).
